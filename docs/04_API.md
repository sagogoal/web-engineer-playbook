# 04. API

---
## 4.1. RESTの基本原則
- [ ] **API-001:** RESTがアーキテクチャスタイルの一種であることを説明できる。
- [ ] **API-002:** 「リソース」中心の設計とは何かを説明できる。
- [ ] **API-003:** URIが「名詞」で表現されるべき理由を説明できる。
- [ ] **API-004:** HTTPメソッド（GET, POST, PUT, DELETE, PATCH）の役割と冪等性を説明できる。
- [ ] **API-005:** `PUT`と`PATCH`の違いを説明できる。
- [ ] **API-006:** ステートレス性とは何か、なぜ重要なのかを説明できる。
- [ ] **API-007:** HATEOAS (Hypermedia as the Engine of Application State) の概念を説明できる。

---
## 4.2. URI設計
- [ ] **API-008:** URIに複数形の名詞を使う（例: `/users`）。
- [ ] **API-009:** URIでリソースの階層関係を表現する（例: `/users/{userId}/posts`）。
- [ ] **API-010:** URIの単語の区切り文字としてハイフン `-` を使う。
- [ ] **API-011:** URIにプログラミング言語の拡張子（`.php`など）を含めない。
- [ ] **API-012:** APIのバージョンをURIに含める（例: `/v1/users`）。

---
## 4.3. リクエスト設計
- [ ] **API-013:** パスパラメータ、クエリパラメータ、リクエストボディの使い分けを説明できる。
- [ ] **API-014:** `GET` の一覧取得APIで、ページネーションのためのクエリパラメータを設計する（`page`, `per_page`など）。
- [ ] **API-015:** `GET` の一覧取得APIで、ソートのためのクエリパラメータを設計する（`sort`, `order`など）。
- [ ] **API-016:** `GET` の一覧取得APIで、フィルタリングのためのクエリパラメータを設計する（`status=published`など）。
- [ ] **API-017:** `POST` でリソースを作成する際のリクエストボディ（JSON）を設計する。
- [ ] **API-018:** HTTPヘッダー（`Content-Type`, `Accept`, `Authorization`）の役割を説明できる。

---
## 4.4. レスポンス設計
- [ ] **API-019:** HTTPステータスコードのカテゴリ（2xx, 3xx, 4xx, 5xx）を説明できる。
- [ ] **API-020:** `200 OK`, `201 Created`, `204 No Content` の使い分けを説明できる。
- [ ] **API-021:** `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found` の使い分けを説明できる。
- [ ] **API-022:** 成功時のレスポンスボディをJSONで設計する（データ本体を`data`キーでラップするなど）。
- [ ] **API-023:** 失敗時のエラーレスポンスの共通フォーマットを設計する（`error_code`, `message`など）。
- [ ] **API-024:** バリデーションエラーの際に、どの項目がなぜエラーなのかを具体的に返すレスポンスを設計する。
- [ ] **API-025:** レスポンスの命名規則として `camelCase` を採用する。

---
## 4.5. APIセキュリティ
- [ ] **API-026:** APIキーを使った認証方式の仕組みを説明できる。
- [ ] **API-027:** セッション認証の仕組みを説明できる。
- [ ] **API-028:** JWT（JSON Web Token）の構造（ヘッダー、ペイロード、署名）を説明できる。
- [ ] **API-029:** JWTの署名を検証する流れを説明できる。
- [ ] **API-030:** JWTのペイロードに含めるべき情報（`iss`, `sub`, `exp`など）を説明できる。
- [ ] **API-031:** JWTのメリット（ステートレス性）とデメリット（失効が難しい）を説明できる。
- [ ] **API-032:** OAuth 2.0がどのような問題を解決するためのものか説明できる（認可の委譲）。
- [ ] **API-033:** OAuth 2.0の登場人物（リソースオーナー、クライアント、認可サーバー、リソースサーバー）を説明できる。
- [ ] **API-034:** OAuth 2.0の代表的なフロー（認可コードフロー）の概要を説明できる。
- [ ] **API-035:** アクセストークンとリフレッシュトークンの役割の違いを説明できる。
- [ ] **API-036:** CORS（オリジン間リソース共有）エラーが発生する原因を説明できる。
- [ ] **API-037:** サーバー側でCORSを許可するためのHTTPヘッダー（`Access-Control-Allow-Origin`）を説明できる。
- [ ] **API-038:** プリフライトリクエスト（`OPTIONS`メソッド）が発行される条件を説明できる。
- [ ] **API-039:** レートリミットの必要性を説明できる。
- [ ] **API-040:** リクエスト内容のバリデーションがなぜセキュリティ上重要なのかを説明できる。

---
## 4.6. APIドキュメンテーションとその他
- [ ] **API-041:** OpenAPI (Swagger) の役割を説明できる。
- [ ] **API-042:** OpenAPI Specification (OAS) をYAML形式で記述する。
  <details>
  <summary>手を動かす</summary>
  - `GET /users/{id}` APIの仕様を、パス、パラメータ、成功・失敗レスポンスを含めてOAS 3.0形式で記述する。
  </details>
- [ ] **API-043:** Postmanやcurlを使って、APIリクエストを送信できる。
- [ ] **API-044:** GraphQLがRESTと比べてどのようなメリットがあるか説明できる（オーバーフェッチ/アンダーフェッチ問題の解決）。
- [ ] **API-045:** gRPCの概要と、RESTとの違い（HTTP/2, Protocol Buffers）を説明できる。
- [ ] **API-046:** Webhookの仕組みを説明できる。
- [ ] **API-047:** Web APIのテスト戦略（単体、結合、E2E）を説明できる。

## 4.7. 発展

- [ ] **API-050:** gRPC-Gatewayの役割を説明できる。

- [ ] **API-053:** `If-None-Match`や`Etag`を使ったHTTPキャッシュの仕組みを説明できる。
- [ ] **API-054:** APIの冪等性を保証するための具体的な設計パターン（冪等キーなど）を説明できる。
- [ ] **API-055:** JSON-RPCの概要を説明できる。
- [ ] **API-056:** WebSocketを使った双方向通信のユースケースを説明できる。
- [ ] **API-057:** API Mock Serverを立て、フロントエンドとバックエンドの並行開発を行う。
- [ ] **API-058:** Dry-run（ドライラン）をサポートするAPIを設計する（`X-Dry-Run`ヘッダーなど）。
- [ ] **API-059:** ロングポーリングの仕組みと、WebSocketとの違いを説明できる。
- [ ] **API-060:** スキーマ駆動開発のメリットを説明できる。
- [ ] **API-061:** 認証と認可の違いを明確に説明できる。
- [ ] **API-062:** ABAC（属性ベースアクセス制御）の基本的な考え方を説明できる。
- [ ] **API-063:** OpenID Connect (OIDC) とOAuth 2.0の違いを説明できる。
- [ ] **API-064:** APIのメトリクス（リクエスト数、レイテンシ、エラーレート）を監視する重要性を説明できる。
