# 09. 運用・監視

リリースしたアプリケーションを安定的に稼働させ、問題が発生した際に迅速に検知・対応するための活動。
システムの状態を可視化し、プロアクティブ（事前対応的）な改善を目指す。

---

## OPS-001 モニタリング

### ゴール

システムの健康状態を把握するために、主要なメトリクス（CPU使用率, メモリ使用率, レイテンシ, エラーレートなど）を監視し、ダッシュボードで可視化できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **何を**監視すべきか？
  - **リソースメトリクス**: CPU, メモリ, ディスク, ネットワーク
  - **アプリケーションメトリクス**:
    - レイテンシ（応答時間）
    - トラフィック（リクエスト数）
    - エラーレート（5xxエラーの割合）
    - サチュレーション（システムの飽和度）
- 監視ツールは何を使うか？ (CloudWatch, Datadog, New Relic)
- **ダッシュボード**は、問題の有無が一目でわかるように設計されているか？
- **正常時の値**を把握しているか？（ベースライン）

---

## OPS-002 アラート

### ゴール

監視メトリクスが事前に定義した閾値を超えた場合に、担当者に自動的に通知（アラート）する仕組みを設計・設定できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **閾値**は適切か？（低すぎるとアラートが頻発し、高すぎると問題を見逃す）
- **通知先**はどこか？ (Slack, PagerDuty, Email)
- **緊急度**に応じて通知方法を変えているか？
- アラートメッセージには、**問題解決に必要な情報**（どのサーバーか、どのメトリクスか、発生時刻など）が含まれているか？
- **アラート疲れ**（対応不要なアラートが多発し、重要なアラートを見逃す状態）に陥っていないか？

---

## OPS-003 ログ

### ゴール

アプリケーションの動作記録（ログ）を適切に出力・収集・分析し、問題調査やデバッグに活用できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **何を**ログに出力すべきか？
  - 重要な処理の開始・終了
  - エラーや例外の発生（スタックトレースを含む）
  - 外部APIとの通信内容
  - ユーザーの重要な操作（ただし個人情報は含めない）
- **ログレベル**（DEBUG, INFO, WARN, ERROR）を使い分けているか？
- ログは**構造化ログ**（JSON形式など）になっているか？（機械的に解析しやすい）
- ログには**コンテキスト情報**（リクエストID, ユーザーIDなど）が含まれているか？
- ログ収集・分析基盤は何を使うか？ (CloudWatch Logs, Datadog, Elasticsearch)
