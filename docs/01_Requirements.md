# 01. 要件定義

---
## 1.1. 要件のインプットと読解
- [ ] **REQ-001:** 「ユーザーストーリー」の基本フォーマット（As a, I want, so that）を説明できる。
  <details>
  <summary>学習のヒント</summary>
  - 「ユーザーストーリー INVEST」で検索し、良いユーザーストーリーの6つの特性を学ぶ。
  </details>
- [ ] **REQ-002:** 「ジョブ理論（JTBD）」の観点から、要件の背景にあるユーザーの「片付けたい用事」は何かを説明できる。
  <details>
  <summary>学習のヒント</summary>
  - 「ドリルを買いに来た人が欲しいのはドリルではなく穴である」という有名な言葉の意味を調べる。
  </details>
- [ ] **REQ-003:** サンプルチケットを元に、目的・背景・ゴールを自分の言葉で説明する。
  <details>
  <summary>手を動かす</summary>
  - 任意のOSSのIssueや、過去の職場のチケットを1つ選び、そのチケットが「誰のどんな課題を解決し、何を達成しようとしているのか」を`README.md`に100字程度で要約する。
  </details>
- [ ] **REQ-004:** 要件に含まれる曖昧な言葉（「など」「適宜」「よしなに」）を特定できる。
- [ ] **REQ-005:** MVP（Minimum Viable Product）のスコープはどこまでかを説明できる。
- [ ] **REQ-006:** 「やること」と「やらないこと」を明確に切り分ける。
  <details>
  <summary>手を動かす</summary>
  - 「ユーザー認証機能」というお題に対し、「やること」（例: メールアドレスでのログイン）と「やらないこと」（例: SNSログイン、パスワードリマインダー）を`README.md`にリストアップする。
  </details>
- [ ] **REQ-007:** プロジェクト固有のドメイン用語やビジネス用語を3つ特定し、その意味を調べる。
- [ ] **REQ-008:** 登場人物（Actor）を「役割（Role）」として全て洗い出せる。

---
## 1.2. 質問とヒアリング
- [ ] **REQ-009:** オープンクエスチョンとクローズドクエスチョンを使い分けて質問を作成できる。
  <details>
  <summary>学習のヒント</summary>
  - 5W1H（Why, What, Who, When, Where, How）を使ってオープンクエスチョンを作成する練習をする。
  </details>
- [ ] **REQ-010:** 質問の意図や背景を添えて、相手が回答しやすい質問文を作成する。
  <details>
  <summary>手を動かす</summary>
  - 「このボタンの色は青ですか？」という質問を、「UIのトンマナを合わせるため、このボタンの色は指定の青（#0000FF）で良いか確認させてください」のように、意図が伝わる形に修正して`README.md`に記述する。
  </details>
- [ ] **REQ-011:** 質問内容に応じて、適切な質問相手（PM, デザイナー, etc.）を判断できる。
- [ ] **REQ-012:** テキストコミュニケーション（Slackなど）での質問の作法を学ぶ。
  <details>
  <summary>学習のヒント</summary>
  - 「Slack 質問 仕方」「チャット コミュニケーション コツ」などで検索し、良いプラクティスを3つ以上見つける。
  </details>

## 1.3. 影響範囲の調査
- [ ] **REQ-013:** `grep`やIDEの全文検索機能を使い、コードベースから特定の文字列が出現するファイルをリストアップできる。
- [ ] **REQ-014:** IDEの「呼び出し階層」や「参照の検索」機能を使い、ある関数がどこから呼ばれているかを特定できる。
- [ ] **REQ-015:** 既存のAPI仕様書を読み、特定のパラメータがどのエンドポイントで使われているかを特定できる。
- [ ] **REQ-016:** ER図を読み、あるテーブルが他のどのテーブルと関連を持っている（FKが設定されている）かを特定できる。
- [ ] **REQ-017:** テーブルのカラム型を変更した場合に、アプリケーションコード側で修正が必要になりそうな箇所を推測できる。
- [ ] **REQ-018:** 共通コンポーネントを変更した場合に、影響を受ける画面をリストアップできる。
- [ ] **REQ-019:** 外部サービスのAPI仕様変更が、自分のシステムにどう影響するか説明できる。

## 1.4. 機能要件の具体化
- [ ] **REQ-020:** ユーザーシナリオ（ハッピーパス）を時系列の箇条書きで記述できる。
- [ ] **REQ-021:** 異常系・例外系のパターンを「入力値」「権限」「データ状態」「外部要因」の観点で洗い出せる。
- [ ] **REQ-022:** ログインフォームの入力項目とバリデーションルールを定義する。
  <details>
  <summary>手を動かす</summary>
  - `README.md`に、メールアドレスとパスワードの項目名、データ型、必須かどうか、文字数制限、正規表現などのルールを表形式で記述する。
  </details>
- [ ] **REQ-023:** バリデーションエラー時のエラーメッセージを、ユーザーに分かりやすい言葉で定義する。
- [ ] **REQ-024:** ユーザー権限（例: 管理者、一般ユーザー）ごとの機能の可否を表形式で定義する。
- [ ] **REQ-025:** 画面に表示する「初期状態」「データあり状態」「データなし状態」「ローディング状態」「エラー状態」を定義できる。
- [ ] **REQ-026:** CRUD（Create, Read, Update, Delete）の観点から機能の抜け漏れがないか確認できる。
- [ ] **REQ-027:** Gherkin形式（Given/When/Then）で受け入れ基準を1つ記述できる。
  <details>
  <summary>手を動かす</summary>
  - `README.md`に「Given: ログインしていないユーザーが, When: ログインページを開き, Then: ログインフォームが表示される」のように記述する。
  </details>

## 1.5. 非機能要件の確認
- [ ] **REQ-028:** パフォーマンス要件について「〇〇秒以内にレスポンスがあること」のように定量的に質問できる。
- [ ] **REQ-029:** 可用性のSLA「99.9%」が、年間の停止時間で何分に相当するかを計算できる。
- [ ] **REQ-030:** セキュリティのOWASP Top 10の項目名を3つ以上挙げられる。
- [ ] **REQ-031:** 個人情報を扱う機能かどうかを確認し、扱う場合は特別な配慮が必要だと指摘できる。
- [ ] **REQ-032:** ログ要件として「誰が・いつ・何をしたか」を記録する必要があるか確認できる。
- [ ] **REQ-033:** 多言語対応の要否について確認できる。

## 1.6. 見積もりと計画
- [ ] **REQ-034:** 1つのユーザーストーリーを、実装に必要なエンジニアリングタスク（半日〜1日単位）に分解できる。
  <details>
  <summary>手を動かす</summary>
  - 「記事投稿機能」というストーリーを、API設計、DBテーブル作成、コーディング、テスト、のように具体的なタスクに分解して`README.md`にリストアップする。
  </details>
- [ ] **REQ-035:** タスクの依存関係を洗い出せる。
- [ ] **REQ-036:** プランニングポーカー（相対見積もり）のやり方を説明できる。
- [ ] **REQ-037:** 見積もりの「不確実性」を考慮する必要性を説明できる。
- [ ] **REQ-038:** 実装方針の選択肢（A案, B案）を挙げ、それぞれのメリット・デメリットを説明できる。
- [ ] **REQ-039:** 技術的負債について説明できる。
- [ ] **REQ-040:** 遅延リスクになりそうな点を1つ以上挙げ、その対策を提案できる。

## 1.8. ドキュメンテーション
