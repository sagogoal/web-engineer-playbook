# 07. テスト

ソフトウェアの品質を保証し、将来の変更に対する安全性を確保するための重要なプロセス。
手動テストを自動化し、バグの早期発見とデグレードの防止を目指す。

---

## TST-001 テストのピラミッド

### ゴール

テストピラミッド（ユニットテスト、インテグレーションテスト、E2Eテスト）の各層の役割と、理想的なテストの割合を説明できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **ユニットテスト (Unit Test)**:
  - 目的: 関数やクラスなど、最小単位のコンポーネントを検証する。
  - 特徴: 高速、安価、分離されている。
  - テスト対象: ビジネスロジック、純粋関数。
- **インテグレーションテスト (Integration Test)**:
  - 目的: 複数のコンポーネントを組み合わせて連携を検証する。
  - 特徴: ユニットテストより遅く、高価。
  - テスト対象: APIとDBの連携、複数コンポーネントのインタラクション。
- **E2Eテスト (End-to-End Test)**:
  - 目的: 実際のユーザー操作を模倣し、システム全体を検証する。
  - 特徴: 最も遅く、高価で不安定。
  - テスト対象: 主要なユーザーシナリオ（例: ユーザー登録からログインまで）。
- 現在のプロジェクトのテストは、このピラミッドの**バランス**が取れているか？

## TST-002 ユニットテスト (Unit Test)

### ゴール

関数やメソッド単位で、期待される入力に対して期待される出力が返されることを検証するテストコードを書ける。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **AAAパターン**（Arrange, Act, Assert）を意識しているか？
  - **Arrange**: テストの前提条件を準備する。（変数の初期化など）
  - **Act**: テスト対象の関数を実行する。
  - **Assert**: 実行結果が期待通りか検証する。
- **テストケース**は十分に網羅されているか？
  - 正常系（ハッピーパス）
  - 異常系（エラーケース）
  - 境界値（0, -1, NULL, 空文字など）
- テストは**独立**しているか？（他のテストケースに依存していないか？）
- **外部依存**（DB、APIなど）は**モック**に置き換えられているか？

## TST-003 モック (Mock)

### ゴール

テスト対象が依存する外部コンポーネント（DB、API、別クラスなど）を偽のオブジェクト（モック）に置き換え、テストを分離できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- なぜモックが必要か？（テストの高速化、安定化、外部依存の排除）
- **スタブ**、**モック**、**スパイ**の違いは何か？
  - スタブ: 事前に定義された値を返す。
  - モック: 呼び出されたかどうかや、引数の検証も行う。
  - スパイ: 実際のオブジェクトをラップし、呼び出し履歴などを記録する。
- どのライブラリを使うか？（Jest, Mockito, RSpecなど）
- モック対象のメソッドが、期待通りに**呼び出されたこと**を検証しているか？
- モック対象のメソッドが、期待する**引数で**呼び出されたことを検証しているか？
