# 12. システム設計

個別の技術要素を組み合わせ、非機能要件（可用性, スケーラビリティ, パフォーマンスなど）を満たす大規模なシステム全体を設計するスキル。
トレードオフを意識した意思決定が重要となる。

### 実務での思考プロセス

- **SPOF (Single Point of Failure)** はどこか？（単一障害点）

  - 複数のアベイラビリティゾーン（AZ）にリソースを分散させる。
- **ヘルスチェック**は行われているか？
  - ロードバランサーが不健康なインスタンスを自動的に切り離す仕組み。
- **フェイルオーバー**の仕組みはあるか？
  - プライマリDBに障害が発生した際に、自動でスタンバイDBに切り替わるか。

## SD-002 スケーラビリティ (Scalability)

### ゴール

システムの負荷増大に対応するためのスケールアップとスケールアウトの違いを説明できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **スケールアップ（垂直スケーリング）**:
  - 概要: サーバーのスペック（CPU, メモリ）を上げる。
  - メリット: シンプルで手軽。
  - デメリット: スペック向上に限界があり、コストが高い。
- **スケールアウト（水平スケーリング）**:
  - 概要: サーバーの台数を増やす。
  - メリット: 理論上は無限にスケールできる。コスト効率が良い。
  - デメリット: システムがステートレスである必要があるなど、設計上の考慮が必要。
- **オートスケーリング**は設定されているか？
  - CPU使用率などのメトリクスに応じて、自動的にサーバー台数を増減させる仕組み。
- アプリケーションは**ステートレス**になっているか？（スケールアウトの前提条件）

## SD-003 キャッシュ

### ゴール

キャッシュを利用してシステムのパフォーマンスを向上させ、バックエンドの負荷を軽減する基本的な戦略を説明できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **何を**キャッシュすべきか？
  - 頻繁にアクセスされるが、あまり更新されないデータ。（例：商品マスタ、設定情報）
- **どこに**キャッシュを置くか？
  - **クライアントサイド**: ブラウザキャッシュ
  - **CDN (Content Delivery Network)**: 静的コンテンツ（画像, CSS, JS）
  - **サーバーサイド**:
    - アプリケーション内のメモリ
    - 専用のキャッシュサーバー（Redis, Memcached）
- **キャッシュの有効期限（TTL）** はどのくらいに設定するか？
- **キャッシュの無効化（パージ）** はどうやって行うか？
- **キャッシュ汚染**（古いデータや誤ったデータがキャッシュされること）への対策は？
