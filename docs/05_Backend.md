# 05. バックエンド

クライアントからのリクエストを受け取り、ビジネスロジックを実行し、データベースとやり取りするなど、アプリケーションの頭脳となる部分。
堅牢性、保守性、拡張性を考慮した設計が重要となる。

---

## BE-001 レイヤードアーキテクチャ

### ゴール

責務の分離を目的としたレイヤードアーキテクチャ（例: プレゼンテーション層, アプリケーション層, ドメイン層, インフラストラクチャ層）の役割を説明できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **プレゼンテーション層 (Controller, GraphQL Resolverなど)**:
  - HTTPリクエストの受付とレスポンスの返却に徹しているか？
  - ビジネスロジックを含んでいないか？
- **アプリケーション層 (Service, UseCaseなど)**:
  - アプリケーション固有の関心事（ユースケース）を実装しているか？
  - トランザクション管理はここで行うべきか？
- **ドメイン層 (Entity, ValueObject, DomainServiceなど)**:
  - ドメインのルールやロジックが凝縮されているか？
  - 特定のフレームワークやインフラに依存していないか？
- **インフラストラクチャ層 (Repository実装, 外部APIクライアントなど)**:
  - DBや外部APIとの具体的な接続処理を実装しているか？
- **依存関係の方向**は守られているか？（上位層は下位層に依存しない）

## BE-002 DI (Dependency Injection)

### ゴール

コンポーネント間の依存関係を外部から注入することで、疎結合な設計を実現できる。

### 完了条件

  - [ ] `README.md`

### 実務での思考プロセス

- なぜDIが必要なのか？（テスト容易性、再利用性、交換可能性の向上）
- **コンストラクタインジェクション**と**セッターインジェクション**の使い分けは？
- DIコンテナの役割は何か？
- `new` キーワードによる直接的なインスタンス化を避けるべきなのはどのような場合か？
- 依存性逆転の法則（DIP）とどう関係しているか？

## BE-003 DTO (Data Transfer Object)

### ゴール

レイヤー間でデータを転送するためのオブジェクトとしてDTOを設計し、使用できる。

### 完了条件

### 実務での思考プロセス

- なぜEntityを直接Controllerから返すべきではないのか？（余分なデータの公開、UI都合の変更がドメインに影響する）
- **RequestDTO**と**ResponseDTO**を区別しているか？
- バリデーションはDTOの責務か？
- DTOとEntityの**変換**はどこで行うべきか？（Service層やDTO自身）
- DTOは**振る舞い（メソッド）を持たない**プレーンなオブジェクトになっているか？
