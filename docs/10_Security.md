# 10. セキュリティ

アプリケーションを悪意のある攻撃から守り、ユーザーのデータを安全に保つための知識と実践。
セキュリティは「一度やれば終わり」ではなく、継続的な取り組みが求められる。

---

## SEC-001 XSS (クロスサイトスクリプティング)

### ゴール

XSSの脆弱性の原理を理解し、その対策（エスケープ処理）を実装できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **脆弱性の原理**:
  - 攻撃者が仕込んだ悪意のあるスクリプトが、ユーザーのブラウザ上で実行されてしまう。
- **影響**:
  - Cookieの窃取（セッションハイジャック）
  - 意図しない操作の実行
  - 偽のページへのリダイレクト
- **どこで発生しやすいか**:
  - ユーザーからの入力をそのまま画面に表示する箇所（検索結果、コメント欄、プロフィールなど）
- **対策**:
  - サーバーサイド: HTMLに出力する全ての変数に対して**エスケープ処理**を行う。（例: `<` を `&lt;` に変換）
  - フロントエンド: React, Vueなどのフレームワークが持つ自動エスケープ機能に頼る。`dangerouslySetInnerHTML`のような危険な機能は使わない。
  - **CSP (Content Security Policy)** の導入。

## SEC-002 CSRF (クロスサイトリクエストフォージェリ)

### ゴール

CSRFの脆弱性の原理を理解し、その対策（CSRFトークン）を実装できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **脆弱性の原理**:
  - ログイン済みのユーザーが、悪意のあるサイトを閲覧することで、意図しないリクエスト（投稿、退会など）を強制的に送信させられる。
- **影響**:
  - 意図しない書き込み
  - 商品の購入
  - アカウント情報の変更
- **対策**:
  - **CSRFトークン**:
    1.  サーバーはフォーム描画時に、ランダムな文字列（トークン）を生成し、Cookieとフォームの両方に埋め込む。
    2.  フォーム送信時、サーバーはCookieのトークンとフォームのトークンが一致するか検証する。
    3.  一致しない場合（＝別サイトからのリクエスト）は処理を拒否する。
  - **SameSite Cookie属性**の設定。

## SEC-003 SQLインジェクション

### ゴール

SQLインジェクションの脆弱性の原理を理解し、その対策（プレースホルダ）を実装できる。

### 完了条件

- [ ] `artifacts` フォルダに成果物を作成する
  - [ ] `README.md`
  - [ ] `anki.csv`
  - [ ] `sample/`

### 実務での思考プロセス

- **脆弱性の原理**:
  - ユーザーからの入力値を直接SQL文に埋め込むことで、攻撃者が意図しないSQL文を実行できてしまう。
- **影響**:
  - データベースの情報漏洩
  - データの改ざん・削除
  - 認証の回避
- **どこで発生しやすいか**:
  - ユーザーからの入力（検索キーワード、IDなど）を使ってSQL文を組み立てている箇所。
- **対策**:
  - **プレースホルダ（Prepared Statement）** を使用する。
    - SQL文の骨格と、埋め込む値を別々にDBに送ることで、入力値がSQL文として解釈されるのを防ぐ。
  - ORM（Object-Relational Mapper）を利用する。（内部でプレースホルダが使われている）
  - 動的にSQLを組み立てる場合は、入力値を厳格にバリデーションする。
